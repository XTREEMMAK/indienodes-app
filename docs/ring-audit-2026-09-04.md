# Ring Audit: verification, traversal, and multipotentiality

Date: 2026-09-04
Scope: three pre-launch questions, audited read-only — whether the site verification step
earns its place given a later approval gate; what actually happens when a visitor uses the
widget on a member's site; and whether the data model has room for a creator with more
than one proficiency.

This is a findings document. No code, workflow, or configuration was changed in this pass.
Two concrete defects surfaced while auditing and are recorded here rather than fixed;
where they belong to an existing tracked gap, they have been threaded into `roadmap.md`
and `open-questions.md` instead of being restated.

## Architecture the audit rests on

Worth stating once, because all three answers depend on it. This repository is a static
SvelteKit app (`adapter-static`, `prerender = true` in `src/routes/+layout.js`). There is
no server here, no database, and no ring logic running server-side — no route handler
resolves "next member," because there is nothing to resolve it on.

Member data lives in a separate repository (`indienodes-ring`) and is consumed as a
published `ring.json`; this repo keeps a byte-for-byte mirror refreshed by
`scripts/sync-ring-mirror.mjs`. The submission, verification, and approval backend is a
set of n8n workflows generated by `scripts/n8n/build_workflows.py`, whose data store is a
set of n8n Data Tables (`scripts/n8n/data-tables-schema.json`).

Three separate systems, then, and several of the findings below are about the seams
between them rather than about any one of them.

## Part 1 — Is the site verification step necessary?

**Conclusion: yes, and it is load-bearing well beyond onboarding.** But the premise the
question started from conflates three distinct things, and separating them is most of the
answer.

### Verification is not the widget check

These are different mechanisms at different times, and the question treated them as one.

**Verification** is a meta tag on the submitter's own page:

```html
<meta name="indienode-verification" content="TOKEN" />
```

n8n fetches the URL and looks for that tag — `wf_reverify_token` in
`scripts/n8n/build_workflows.py:589`, using a real `extractHtmlContent` parser node
(`:868`) rather than a regex, so unquoted values and odd attribute order are not special
cases. Redirects are deliberately not followed, which is the SSRF boundary.

**The widget embed** is not asked for at submission at all. It is handed out on the
`/join` success screen _after_ approval (`src/routes/join/+page.svelte:935-1005`), and
whether a member still carries it is checked afterwards by the participation validator
that now lives in `indienodes-ring` (the `ring_widget_site_id_unmatched` result referenced
in `roadmap.md`).

So the sequence the question described — someone adds a widget, verifies, and still isn't
in the ring — is not a sequence this flow produces. Nothing requests a widget before
approval, and verification costs the submitter one meta tag, not an embed.

### Verification and approval answer different questions

Verification asks _does this person control this URL_. Approval asks _should this creator
be in the ring_. One is authentication, the other is curation, and approval cannot absorb
verification because a maintainer reading a queue row has no independent way to tell
whether the submitter controls the site they named. Without the check, the honest version
of the review step would be "approve this person's claim about someone else's website."

The reasoning for why the token is backend-issued and bound to a stored `source_url` is
already recorded at `decisions.md:1339` and is worth re-reading rather than restating: a
submitter-chosen token can be one already present on a page they have never had access to,
and a URL supplied at check time can differ from the one finally submitted. Either makes
the step decorative. The current design closes both — `verify` sends only a
`submission_id` (`src/lib/submissionApi.js:14-21`), and `bind_source_url` is once-only
(`build_workflows.py:1028-1055`).

### The decisive point: it is the auth substrate for the whole node lifecycle

This project has no accounts, by design. That means ownership verification is not merely
the first gate in onboarding — it is the **only** mechanism the ring has for telling a
member from a stranger, at every later point where that question is asked.

Both later points already depend on it. `/update` and `request_removal` authenticate by
re-running the same ownership check, against a `source_url` read from the **live ring**
rather than from the request body — `find_node_js` at `build_workflows.py:995-1005`:

> The URL to re-verify against always comes from the live ring, never the request body.
> If a caller could name it, ownership verification would be decorative.

Removing verification from onboarding would therefore not remove the mechanism. It would
move its first use later, to the moment someone asks to edit or withdraw an entry — and
leave the ring, in the meantime, unable to distinguish a member from anyone who knows
their node id.

The state machine also already guarantees ordering rather than documenting it: a row
cannot reach `pending_review` except through `verified` (`build_workflows.py:1324-1360`),
and the check is re-run server-side at submit rather than looked up, outside a 90-second
window (`REVERIFY_SKIP_TTL_SECONDS`, `:193`). A maintainer never sees an unverified
submission.

### The friction, named honestly

Two real costs. Neither is fatal, and neither is an argument for removal:

- **The generator branch is heavier than the own-site branch.** A creator with no site of
  their own must export, upload, and only then verify via `bind_source_url`. This is
  inherent rather than incidental: the token has to be baked into the exported HTML before
  a URL exists to bind it to (`decisions.md:1385`). The own-site branch is a single pasted
  tag.
- **`TOKEN_TTL_SECONDS` is 24 hours** (`build_workflows.py:179`), so a submission
  abandoned and resumed a day later starts over.

If the verification step is ever revisited, the generator branch's round trip is the part
worth attacking — not the check itself.

### Drift found while auditing

`schema/ring.schema.json` still lists `verification_token` in `required` (`:27`), but the
approval allowlist never emits it (`build_workflows.py:2409`), and the token is explicitly
cleared when a row enters review. Every entry the workflow now produces would fail the
schema as written.

This is known and deliberate cross-repo lag, documented at `src/lib/ring.js:22` ("Legacy
field; new approvals do not publish it") and in `src/lib/submissionValidation.test.js`.
Resolution belongs to `indienodes-ring`, not here. Noted so the audit is not read as
having missed it. The two live entries in `ring.json` still carry legacy tokens.

**Resolved 2026-09-12, the other way.** The ring's schema was never relaxed, and its
`member-health.js` reads `verification_token` to re-check the creator's tag, so the lag surfaced
as ring PR #30 failing `validate:publish`. Approval publishes the checked token again and refuses
to open a PR without one.

### Recommendation

**Keep verification exactly where it is.** It is cheap for the submitter on the common
path, it is the only anti-impersonation control the ring has, and it is already the
authentication mechanism for update and removal — so it cannot be removed, only relocated,
and relocating it weakens the `source_url` binding that makes it mean anything.

## Part 2 — Ring traversal, end to end

The question was: when someone adds the widget and a visitor interacts with it, what
request is made to track ring position, and where does it refer to based on current
position?

**Direct answer: no request is made, and none tracks position.** There is no analytics
call, no beacon, no impression or click record — deliberately, and recorded as a decision
rather than an omission (`open-questions.md:41`, "including aggregate embed counts, and
none are planned"). The only server-visible trace is Caddy's own access log, which nothing
in this repo consumes.

### What actually happens

One `GET` of the whole `ring.json`, with no parameters, on widget mount
(`src/widget/Widget.svelte:57-69`). After that, everything is in memory:

- **Position** is the array index of the entry whose `id` matches the `site-id` the member
  pasted into the snippet (`:61`).
- **Prev / Next** are `index ± 1` with double-modulo wraparound; **Random** picks
  uniformly and excludes the current entry (`:83-103`).
- **Travel** is `window.open(entry.source_url, '_blank', 'noopener,noreferrer')` — a new
  tab, deliberately, rather than navigating the host's page away.

**Ring order is the raw array order of `ring.json`** as published by the ring repo.
Nothing sorts it client-side; there is no ordering column and no `joined_at` sort. The
`/members` page's alphabetical sort is display-only and does not feed the widget.

### The four tiers do not all have a position

This matters for the "both the full and text widget" half of the question. The tiers
(`src/lib/widgetTiers.js:27-49`) are four independent artifacts, not visual variants:

| Tier            | What it is                                  | Has ring position?   |
| --------------- | ------------------------------------------- | -------------------- |
| `widget`        | sandboxed iframe → `/embed-frame?site-id=`  | yes, via query param |
| `widget-script` | `<script>` + `<indienode-widget site-id>`   | yes, via attribute   |
| `badge`         | `<a href="/go/random"><img 88×31></a>`      | **no**               |
| `text-link`     | `<a href="/go/random">` — the "text widget" | **no**               |

The text tier has **no Prev, no Next, and no ring position at all.** It is a plain anchor
with a fixed phrase, deliberately not allowed a script of its own, and its only behavior is
a random hop through `/go/random` (`src/routes/go/random/+page.svelte`). Worth stating
plainly because "test the text widget's ring position" is not a test that can be written —
there is nothing there to exercise. The same is true of the badge.

One asymmetry to know when testing: `/go/random` applies the explicit-content gate
(`isVisibleTo`), while the widget's own Random cannot, because it runs on a third-party
origin with no access to visitor preferences. Intentional, recorded at `decisions.md:1481`.

### Gaps

**1. `/embed-frame`'s CSP blocks its own ring fetch in production.** The per-path override
sets `connect-src 'self'` (`Caddyfile:191`), while production sets
`VITE_RING_URL=https://ring.indienodes.us` (`decisions.md:1946`, supplied via
`.github/workflows/docker-publish.yml:149`). The site-wide policy lists that origin
(`Caddyfile:101`); the `/embed-frame` override does not, and its own comment concedes the
case — "add that origin here if one is ever configured for this deployment."

Not a hard break: `loadRing` falls back to the same-origin mirror when the primary fetch
fails (`src/lib/ring.js:404-411`), and a CSP-blocked fetch rejects in a way that catch
handles. But the effect is that the **default, recommended** widget tier throws a CSP
violation on every load and silently serves the five-minute-cached mirror instead of the
canonical endpoint. `testing/csp.e2e.js` cannot catch this — the e2e build configures no
`VITE_RING_URL`, so the policy under test is not the policy in production.

This is the highest-value finding in Part 2, because it is on the path the project
actively recommends and it fails invisibly.

**2. There is no cross-origin harness, and the ring has never been traversed.** The fixture
member sites under `testing/sites/` carry their verification meta tags but **no widget
embed of any kind** — verified, the grep returns nothing. So the ring's actual purpose,
moving a visitor from one member's site to another, has never been exercised end to end.
`testing/embed-frame.e2e.js:6-11` says as much about itself.

Worth recording that this is closer to hand than it reads: `testing/scripts/serve.mjs`
already serves those sites on port 4174 with `Access-Control-Allow-Origin: *`, which is a
second real origin. The missing pieces are embed markup in the fixture pages and a spec
that drives a traversal across them.

**3. `ring.indienodes.us`'s own CORS is unverified from this repo.**
`src/lib/widgetCors.test.js` parses the Caddyfile and asserts it covers `RING_JSON_URL`'s
path — but the widget's _primary_ endpoint is `RING_ENDPOINT_URL`, whose origin lives in a
different repository and deploy. If that host omits `Access-Control-Allow-Origin`, the
full widget fails on every member site while the badge and text tiers keep working, which
is precisely the silent-failure signature the `@embeddable` block exists to prevent.

**4. A stale or unedited `site-id` fails invisibly.** No warning, no visible difference —
Prev and Next simply start from a random point (`src/widget/Widget.svelte:62`, a
deliberate choice over pretending everyone is entry zero). Already on the roadmap's
widget-validation checklist as the likeliest failure; reinforced here rather than
restated.

### Recommendation

Findings 1–3 are threaded into `roadmap.md`'s existing "Widget validation" section, which
is already marked release-required. Finding 1 should be treated as a defect to fix rather
than a case to test, and it is a one-line Caddyfile change plus a test that can actually
see it.

## Part 3 — Multipotentiality nodes

The question was whether a creator with more than one proficiency — an artist who is also
a musician — is handled, with a recollection that separate node submissions loosely cover
it.

**That recollection is correct, and it is deliberate rather than incidental. The mechanism
exists, is LOCKED, and is currently inert.**

### What is already in place

`creator_id` is an optional, backend-assigned field that links one creator's nodes without
merging them (`schema/ring.schema.json:42-47`, LOCKED at `decisions.md:1391`). It is a
data-only link — nothing ranks or weights on it — and **at most two nodes may share one**,
enforced as a moderation-checklist rule rather than in the schema.

The supporting display decision is already built. Because `title` was removed, two nodes
from the same creator needed something else to tell them apart at a glance, and the
addendum's answer was a prominent `type` badge. That exists on both surfaces where it
matters: the field card (`src/components/FieldNode.svelte:478`) and the members list
(`src/routes/members/+page.svelte:255`), where entries are also sorted by creator, so a
creator's two nodes land adjacent.

So the intended model for an artist/musician is: **two linked nodes, one per type, visibly
distinguished by badge.** Not one node with two media kinds.

### What is not in place

**`creator_id` is never assigned to anyone.** The matcher only _propagates_ an id from an
existing entry that already carries one (`build_workflows.py:2390-2395`):

```js
const match = ring.find((e) => e && hostOf(e.source_url) === host && e.creator_id);
if (match) creator_id = match.creator_id;
```

Nothing mints the first one. The first node from a host therefore gets `null`; the second
node from that same host finds no match — because the first has no `creator_id` to
propagate — and also gets `null`. The chain has no origin, so it never starts.

This is a _different_ bug from the one already fixed. A prior `ReferenceError` (`new URL()`
is not available in the n8n Code sandbox) made the whole block throw and be swallowed,
which is documented at `:2379`. That was repaired by hand-rolling `hostOf`. The bootstrap
gap survives the repair.

Nothing catches it, either. The n8n Code-node tests exercise this exact node but assert
only on `.json.id` (`scripts/n8n/test_code_nodes.mjs:1280`), never on `creator_id`. And
nothing reader-side consumes the field: the only references in `src/` are a typedef
(`src/lib/ring.js:7`) and two comments in `submissionValidation.js`. Neither live entry in
`ring.json` carries one.

The practical consequence: the "also by this creator" surface, and any pairing rule built
on `creator_id`, would evaluate against an empty set today.

### Do not widen `type` to be multi-valued

Recorded as this audit's clear advice, since it is the obvious first instinct for
"multipotentiality" and it is the wrong move.

`type` is a single immutable enum, and it is enforced independently in five places: the
JSON Schema (`ring.schema.json:48-51`), `submissionValidation.js`'s validate, its
`toRingEntry` serializer — which actively **discards** any media array that does not match
the chosen type — the n8n publish allowlist (`build_workflows.py:2409`), and the `/update`
lock that makes `type` uneditable after joining. Widening it would ripple further still,
into `coverImageUrl`, `hasValidShape`, `nodeShape.ALLOWED_RATIOS`,
`nodeChannel.matchesType`, `resolveNodeStage`, the per-type rotation preferences, and
Ambient's own pool split.

It also contradicts a decision already locked: "Node = creator. Hero = work."
(`decisions.md:1768`). A creator's works are evidence inside one node, not a collection of
nodes — and a multi-typed node would reopen exactly that.

**Two linked nodes is the right shape.** It just needs to actually work.

### The Ambient question

Today Ambient deals from two independent decks (`src/components/AmbientView.svelte:105-120`):
`audioPool` is `type === 'audio'` with at least one playable track; `visualPool` is
everything else. A node is either audio or visual, never both, so the "show music and art
at the same time" state is not representable within one node — but **an artist/musician's
two linked nodes can already co-occur, purely by chance**, uncoordinated and with nothing
saying they belong to the same person.

The file names this a placeholder rather than a design (`:6-11`): pairing is `pairs_with`,
still an open data-model question, and inventing a relationship in the client "would make
this first pass look more authoritative than it is."

Three readings:

- **Leave them independent.** Zero work, honest about what it is. But the co-occurrence
  stays accidental, and when it does happen the view says nothing about it — the one
  moment the ring could feel authored passes unremarked.
- **Suppress co-occurrence.** Treat one creator filling both lanes as a bug and deal
  around it. Cheap, and defensible on "no single creator owns the screen." But it spends
  effort specifically to discard the most coherent pairing the ring can produce.
- **Deliberately pair them, sometimes, and make the pairing legible.** _Recommended._

### Recommendation

Treat `creator_id` as the first, free implementation of `pairs_with`.

The reason this is worth doing is sequencing, not novelty. `open-questions.md:45` records
`pairs_with` as blocked on the submission form existing before "creator-submitted" pairing
is even meaningful, and `roadmap.md:316` calls the two-deck deal a placeholder pending
that. But a creator's own music under their own art needs **no new submission field and no
new judgment** — the relationship is already asserted by the same person, through the
`creator_id` link the schema already carries. It is the one pairing this project can make
without inventing data, which is the exact objection `AmbientView`'s comment raises against
pairing today.

Two constraints belong in the recommendation, not as caveats but as part of it:

- **Occasional, not default.** The two-deck deal should stay the normal behavior, with a
  creator pairing surfacing sometimes. Pairing every time one creator has two nodes turns a
  nice moment into that creator holding both lanes for as long as the pair rotates — which
  is the legitimate worry behind "or still played separately."
- **Legible when it happens.** If the view is going to assert that these two things belong
  together, it should say so. An unlabeled pairing is indistinguishable from the chance
  co-occurrence that already happens, which means it buys nothing.

**This is blocked on data, not design.** Until `creator_id` is actually minted, every
pairing rule evaluates against an empty set and cannot be assessed against real behavior.
Fixing the bootstrap gap is the prerequisite for the rest, and is small — the missing piece
is minting an id for the first node of a host rather than only propagating an existing one,
plus a test that asserts on `creator_id` at all.
